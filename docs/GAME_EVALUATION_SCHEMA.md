# 原始游戏资源驱动的评测输入、自动建图与五类记忆

更新：2026-10-30。状态：**四列独立记录设计；自动建图已有离线实现，真实效果待验证**。本版替代此前“先人工补齐 context 和实体身份，再交给 agent”的主流程。目标是尽量保留原始游戏文本及资源组织，让 agent 自己完成实体发现、关系提取、检索与翻译。配套记忆方案见 [MODULAR_GAME_MEMORY_PLAN.md](MODULAR_GAME_MEMORY_PLAN.md)。

## 实施更新（2026-10-30）

四列 CSV 桥接、从空实体表发现/跨批次复用、实体间关系候选与单独模型复核、图派生身份/主题及最小逐条翻译记忆集成已实现。实际API、验证与剩余限制见 [AUTO_GRAPH.md](AUTO_GRAPH.md)。本次移除 group_id 和原生组批处理，改为独立记录按行数分批；下文其他“待实现”内容需结合实际入口理解；完整 LangGraph 工作流、真实模型效果与全局实体维护仍未完成。

## 1. 重新明确研究对象

用户希望测试的是：给定游戏原文及正常能取得的原生资源结构，agent 能否自行发现分散知识、构建实体关系图，并提高本地化翻译质量。

因此，人工补写人物背景、主题标签、实体链接和场景说明，不应成为主评测输入的前提。人工可以审核数据是否提取完整、源译文是否对齐，以及制作离线参考/关系标注；这些工作不能提前替系统完成测试阶段的实体识别和消歧。

需要区分两种 context：

- **原生上下文**：原文件、对象块、字段名、原生 ID、原有注释、明确引用、对话节点。这些本来就存在，可以保留或无损解析。
- **推导上下文**：模型总结的背景、识别出的说话人、实体归属、主题和关系。这些是 agent 的中间产物，不能默认作为人工整理好的输入答案。

**不需要强制填写一个人工 context 列，但需要让 agent 有机会读取原资源中本来存在的局部信息。** 如果只剩一句话且没有其他线索，未知身份和场景可以始终未知。

## 2. 输入用什么格式、包含哪些字段

### 2.1 优先保留实际取得的原文件组织

Flare 原始材料是模块化 txt 与源码，可以直接保留目录及文件；其中的配置语法不应因为扩展名是 txt 就被当成无结构纯文本。其他游戏如果已经导出 CSV，就保留模块化 CSV。无需为了研究统一改写游戏正文。

适配层只负责找到可翻译字符串、分配稳定记录 ID，并保留它们在原资源中的位置。它可以解析已知格式，不提前生成自然语言背景。

适配器允许转义还原和字段解析，但应能核对回原字段值；不能把拼写修正、语气改写或译者解释混进 source_text。文件布局和重复使用位置也不因文本相同而合并。

### 2.2 给实体关系提取 LLM 的四列 CSV

提取输入统一采用以下设计，字段解释、Flare 案例与批处理约定见 [轻量记忆方案第 4 节](MODULAR_GAME_MEMORY_PLAN.md#4-实体和关系怎样提取只做有用的部分)：

```csv
id,source_text,text_type,context
```

- `id/source_text` 必填；`text_type` 按原生用途映射，不明确时为 unknown。
- 每行独立，不设置 group_id，也不增加外层分组；仅按批次大小读取，同批或相邻不能证明归属。
- `context` 用简单键值文本保留发话角色、出现条件、明确引用等必要原生线索，无信息时留空。它不是人工写好的背景或模型总结。
- 文件/key、源版本与使用位置按 ID 保存在后台，不扩充提取表；共享文本的不同使用位置仍保留独立记录。

不要求填写 speaker_id、entity_id、topic_id 或关系列。原生发话信息可进入 context，实体身份与关系由系统提取、核验；不把整理 CSV 变成人工预先建图。

该四列提取输入由 `import_benchmark()` 接入，不替换已有 `localization-text/0.2` 存储契约；后者的 context 仍是对象。它也不同于包含参考译文的四列人工查看表，不能混用。

### 2.3 保留必要线索，但不强制恢复分组

原始文件与位置可以留在后台用于溯源；原生发话标记、出现条件、控件用途等必要线索保留在各行 context。模型输入不附对象组、对话块或模块分组包装，不因删除 group_id 而要求人工把这些结构改写为背景段落。

代价是：仅凭独立名称与模糊描述，可能无法确定归属。允许未知和未链接，不按相邻行补全关系。所有对照使用一致的源侧可见范围；额外读取原文件或补充结构的实验需单独声明，不把额外资料收益都算成图算法收益。

## 3. context 在流程中的位置

推荐流程：

```text
原始模块文件/CSV
  → 规则适配：抽取四列独立记录，来源位置留在后台
  → agent 按批次大小读取独立记录，不附分组
  → 自动发现实体、提及和关系
  → 核验与消歧，生成图
  → 当前句查询图、其他原文及五类记忆
  → 临时组成当前翻译所需的上下文
  → 翻译、检查、写入本次运行记忆
```

这里实际喂给翻译模型的 context 是检索与记忆模块生成的，而不是数据整理人员为每条文本预写的背景。

按批次大小读取并保留每句 ID，不要求同一原生对象的文本一起输入。技术分块只用于模型输入，不表示同场景、同人物或时间连续。所有关系最终指向具体文本 ID，不能只保存“第几个批次”。

## 4. 建图必须同时覆盖实体发现与两类关系

### 4.1 两类节点即可

- **Text**：现有 occurrence，对应原始文本记录。
- **Entity**：character、skill、item、location、organization、quest 等；由源侧材料发现，不要求预先提供完整实体表。

text_type 是文本用途属性，不能代替句子中的实体抽取。skill_description 中可能同时提到别的技能、物品或组织；台词也可能包含多个实体。

不必把每个形容词、数值和抽象概念都建成实体。先提取稳定可指称、能帮助跨文本检索的对象；技能数值可先保留为定义文本中的属性。

### 4.2 文本—实体关系

| 关系 | 含义 | 从哪里得到 |
| --- | --- | --- |
| MENTIONS | 文本提到实体 | 句子/段落中的明确提及及消歧 |
| DEFINES | 文本命名或解释实体 | 定义语句、原生 name/description 对象块 |
| SPOKEN_BY | 文本由某人物说出 | 原生说话字段、明确话语标记；不是人物在句中被提到 |
| ADDRESSED_TO | 明确说话对象 | 原生字段或足够明确的文本；缺失则不连 |

假设某句是 “Arin is a member of the Order.”，它会发现 Arin 和 the Order，并建立两条 MENTIONS。不能因此建立 `这句话 SPOKEN_BY Arin`。

Flare 中 NPC 头部来自 INCLUDE 公共文件，him/her/you 字段能提供发话结构；可用引擎适配规则解析。若只给这句英文，没有发话结构，agent 就应允许说话人未知。

### 4.3 实体—实体关系

同一句 “Arin is a member of the Order.” 还可以产生：

```text
Arin ─ MEMBER_OF → the Order
```

这种关系来自句子含义，不能只靠 text_type 或文件归属取得。首版可复用 MEMBER_OF、LOCATED_IN、COUNTERS；其他确有需要的关系按现有 RelationType 扩展，避免无限自由生成关系名称。

抽取提示词必须允许“没有足够关系”。共享一个文件、相邻出现或向量相似不直接生成实体事实。否定、条件和转述要保留；例如“曾属于”“不属于”“如果加入”不能都写成无条件 MEMBER_OF。

### 4.4 无需人工实体表的两步提取

1. **发现**：按句/段读源材料，输出实体提及、类型、原文位置、候选关系。可先读名称与说明资源帮助冷启动，再处理台词；这只是工作调度。
2. **连接**：与已发现实体表比较，结合原生 ID、名称、别名和附近原文决定复用或新增身份。不确定就暂不合并；必要时查询其他模块补证。

实体表是 agent 自动积累的产物，之后可以作为后续批次的候选提示。不能为了方便而从测试中文参考抽别名；也不能把待比较方法产生的实体/目标记忆混用。

格式、引用存在和端点类型可由程序检查；语义矛盾、歧义和关键关系可由独立模型审查。模型自报置信度不是事实正确的证明。主自动实验不依赖人工逐边批准；若现有接口要求批准状态，后续需实现明确的自动核验准入路径，保留失败/未决项，不能直接把全部候选改成 approved。

## 5. 规则与人工各做什么

| 环节 | 推荐职责 |
| --- | --- |
| 规则适配器 | 找可翻译字段、保留正文/原生字段、展开明确引用、分配记录 ID、提取占位符 |
| 建图 agent | 新实体发现、提及链接、语义关系抽取、歧义处理、检索补证 |
| 人工数据审核 | 核对漏提/错提、原文是否改变、参考对齐和翻译品质 |
| 人工离线标注 | 少量实体/关系真值和必要证据标签，用于评价 agent；不输入主实验 |

原生 speaker_id 被规则读出后可以确定性建边；缺失 speaker_id 时，不能用人工补齐来掩盖系统无法识别的问题。人工协助实验可以保留，但应单列，说明修改内容及工作量。

因此，人工审核源数据不等于人工润色语境。主数据集不需要为每句写一段说明，也不需要提前建成正确图。

## 6. 五类记忆仍然适用，组织键由系统产生

| 记忆 | 内容及来源 |
| --- | --- |
| 术语 | 自动发现的实体名称、候选译名；经核验的本 run 译文逐步积累，不能用测试参考初始化 |
| 摘要 | 从实体关联原文和本 run 已验证译文生成主题概览；不是全人物文件的剧情总结 |
| STM | 图关联/检索得到的近期相关已验证译例，代表工作历史 |
| LTM | 同 run 的远期相关译例，按实体和源文相似度召回 |
| 角色记忆 | 已明确人物身份的源侧风格证据与核验后的笔记；身份未知时不套用 |

topic_id 和 speaker_id 可以作为 agent 的内部结果，不应强制数据整理人员填入。没有主题时仍可使用词法/向量检索；没有相关译例时 STM 为空，不阻断翻译。

摘要应从有效底层证据重建，不能反过来当作证明原始关系正确的独立证据；避免“猜出关系→写成摘要→再抽取并确认同一关系”的循环。源文、实体链接或关系失效时，沿现有依赖机制使相关派生记忆失效。

## 7. 评测集怎样保持公平

### 7.1 最小文件组织

```text
raw/                 原始模块文件；实际无法取得时可缺省
source.jsonl         稳定ID、原文、类型及原生可用信息
references.jsonl     参考译文，仅离线评分
splits.jsonl         数据划分及分组，仅实验管理
```

语言、游戏版本和可见范围沿用已有数据说明。人工实体/关系标签只在需要评价抽取质量时另存，不属于 source。模型生成图与摘要放在运行产物中，不作为人工完善的静态输入。

### 7.2 已有 Flare context 需要怎样使用

目前 source.jsonl 中已经有可读 speaker、skill_name、previous/next、usage 等：

- 从原生字段确定性读出的信息，可以作为“含原生结构”设定使用；记录具体来源规则。
- 为方便翻译而复制的前后文、拼装的说明属于适配后的输入视图。它不是人工答案，但必须对所有对照保持一致；测试图的上下文发现能力时，优先让系统按 ID 自行检索原文，避免提前把所有相关资料塞到每行。
- 需要人工语义判断才能得到的主题/背景，不自动加入主输入。
- 保留原始发布数据，通过实验输入视图控制字段，不原地抹掉已有数据。

不要只给图方法结构丰富的 Flare 输入，再用孤立句子基线比较。比较图组织能力时固定相同源库和输入范围；比较原生元数据价值时单独做消融。

### 7.3 数据划分和指标

对话按已有局部块，技能/物品按对象及模板族分组；检查相同 key、同源文本与近似模板跨划分重复。源侧组信息可以由实验管理器使用，不意味着把人工任务标签交给模型。不能按人物文件或 CSV 行简单随机切分。

当前 Flare 上游参考未经全面人工评级，先审定评分子集。旧 Demo/开发模块与当前主战役分开报告。缺参考文本可以作为声明允许的源资料，但不能混入有参考评分的分母。

所有方法固定同一处理顺序、上下文预算及源侧可见范围，独立积累目标记忆；可额外测试几个固定的组顺序。报告按类别的翻译指标、实体链接/关系准确性、必要资料召回、错误场景推断和成本。

sCOMET 可用于有参考记录；短名称需结合术语一致性与人工检查。dCOMET 仅用于有可靠篇章结构的子集，不把技能列表或整个 NPC 文件当成一篇故事。人工正确图仅用于单列的上限实验，不能冒充自动建图结果。

## 8. 当前代码与该设计的差距

已有：原文/参考分离、Flare 规则提取、源侧位置与部分局部结构、版本化图、五类记忆及游戏模式。

仍需后续实施：

1. M1 JSONL/原生结构到 M2/M3 的统一桥接；保留原文和位置，不要求人工主题。
2. **自动发现新实体**。目前 [EntityLinker](../src/localization_agent/retrieval/extraction.py) 需要调用方提供已登记实体，只能提出到这些实体的部分链接，尚不等于完整自动建图。
3. 句子/段落中的实体—实体关系抽取与自动核验。现有图能存自定义关系，当前提取入口却只输出 MENTIONS/DEFINES/SPOKEN_BY。
4. 把系统发现的实体与主题自动用于摘要/角色记忆；现有手工指定 topic 或实体的演示只能验证接口。
5. 小规模人工离线标注及自动图/无图对照，核实改进来自系统能力。

本轮修订仅调整设计文档，未改动原始数据或运行代码。后续实现重点是让 agent 从原始材料发现结构，而不是继续增加输入表必填字段。
